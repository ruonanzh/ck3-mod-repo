# CK3 modding docs index

A curated map of the knowledge layer under `docs/`.
**Load selectively.** Read this index first. Then open only the one or two pages that the current
task needs, instead of pulling the whole `docs/` directory into context.

## Lookup hierarchy (which source is authoritative for what)

| You need | Source |
|---|---|
| Exact vanilla object definitions, field values, and loc keys | `game-scripts/game/game/` — the script mirror that `sync_game_scripts` generates (two `game/` levels). Never grep the install directory instead |
| The parameters and the scope of one effect, trigger, modifier, or scope | [`wiki/`](wiki/README.md), the shipped snapshot of the wiki reference lists |
| "How do I add a building / trait / decision / …" | [`wiki/`](wiki/README.md): one page per content kind. There is no building page; [`wiki/Holdings_modding.md`](wiki/Holdings_modding.md) covers it |
| Whether a wiki page exists at all (including the pages not shipped) | [`wiki/INDEX.md`](wiki/INDEX.md) — one row per page, with `Local = yes/no` |
| Whether a name still exists in the **installed** version | `game-scripts/script-docs/*.log`, generated by `node scripts/dump-script-docs.mjs`. It is version-exact and beats the `wiki/` snapshot |
| Script language rules (syntax, scopes, variables, iterators, templates) | [`wiki/Scripting.md`](wiki/Scripting.md) |
| Mechanics concepts and how-to method (mod API) | the official wiki (ck3.paradoxwikis.com). When it is unreachable, the snapshot under `wiki/` is the offline substitute |
| The modding conventions and the reason behind them | [`ck3-modding-conventions.md`](ck3-modding-conventions.md) |

- **Start here:** [`ck3-modding-conventions.md`](ck3-modding-conventions.md). This cheat-sheet
  covers override (LIOS/FIOS), load order, localization, the `descriptor.mod`/`.mod` metadata, and
  the entry mechanisms. It answers most modding questions on its own. Read the pages below only when
  you need more depth.

## How a player request becomes a mod

A feature request is a route through this knowledge layer, not a guess. The stages are the same every
time; only the page changes.

| # | Stage | Read or run |
| --- | --- | --- |
| 1 | **Map the request to one page** | [`wiki/INDEX.md`](wiki/INDEX.md), one row per page with `Local = yes/no` |
| 2 | **Read that page's mechanism** | The one section the request needs, not the whole page |
| 3 | **Locate the entry in vanilla** | `game-scripts/` by grep, or `entry-scout` — peers, and the scout is preferred because it runs in parallel |
| 4 | **Check the call form** | `wiki/Effects_list.md`, `Triggers_list.md`, `Modifier_list.md`, `Scopes_list.md`; `script-docs/*.log` when present |
| 5 | **Agree, write, verify** | The player, then `validate_mod` |

The `mod-creator` skill states the same pipeline with its rules. Stage 1 belongs to the main agent:
choosing the mechanism is a decision, and `entry-scout` only locates a name.

> `validate_mod` checks **syntax and conventions** only: balanced braces and quotes, the
> localization format, and the `descriptor.mod` fields. It does **not** check effect, trigger, or
> modifier names, and it is not a scope or type validator. Use `game-scripts/` and the official wiki
> for those.
