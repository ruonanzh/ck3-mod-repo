# CK3 modding docs index

A curated map of the knowledge layer under `docs/`.
**Load selectively.** Read this index first. Then open only the one or two pages that the current
task needs, instead of pulling the whole `docs/` directory into context.

## Lookup hierarchy (which source is authoritative for what)

| You need | Source |
|---|---|
| Exact vanilla object definitions, field values, and loc keys | `game-scripts/vanilla/game/` — the script mirror that `sync_game_scripts` generates (a copy of the game directory, so the scripts sit one level down). Never grep the install directory instead |
| The parameters and the scope of one effect, trigger, modifier, or scope | [`wiki/`](wiki/README.md), the shipped snapshot of the wiki reference lists |
| "How do I add a building / trait / decision / …" | [`wiki/`](wiki/README.md): one page per content kind. There is no building page. [`wiki/Holdings_modding.md`](wiki/Holdings_modding.md) covers it |
| Whether a wiki page exists at all (including the pages not shipped) | [`wiki/INDEX.md`](wiki/INDEX.md) — one row per page, with `Local = yes/no` |
| Whether a name still exists in the **installed** version | `docs/script_docs/*.log`, generated by `node scripts/dump-script-docs.mjs` and committed. It is version-exact and beats the `wiki/` snapshot |
| Script language rules (syntax, scopes, variables, iterators, templates) | [`wiki/Scripting.md`](wiki/Scripting.md) |
| Mechanics concepts and how-to method (mod API) | the official wiki (ck3.paradoxwikis.com). When it is unreachable, the snapshot under `wiki/` is the offline substitute |
| The modding conventions and the reason behind them | [`ck3-modding-conventions.md`](ck3-modding-conventions.md) |

  the entry mechanisms. It answers most modding questions on its own. Read the pages below only when

## How a player request becomes a mod

A feature request is a route through this knowledge layer, not a guess. It runs in two stages, and
the full step list is in the `mod-creator` skill.

| Stage | What it settles | Where the detail is |
| --- | --- | --- |
| 1. Settle the request and the mount point | The page, the mechanism, the vanilla entry, and the window's own `.gui` file | `mod-creator`, Stage 1, steps 1–5 |
| 2. Write and check | The override form, the files, `validate_mod`, and `mod-reviewer` | `mod-creator`, Stage 2, steps 6–9 |

Choosing the mechanism is a decision, and `entry-scout` only locates a name. The call form of an
effect, trigger, modifier, or scope comes from the reference lists in [`wiki/`](wiki/README.md) and
from `docs/script_docs/`.

> `validate_mod` checks **syntax, conventions, and names**: balanced braces and quotes, the
> localization format, the `descriptor.mod` fields, the localization keys of a new trait, decision, or
> character interaction, and an effect, trigger, or modifier name that is close to a real game name.
> It is not a scope or type validator, and a `PASS` does not prove that a new name exists. Use
> `game-scripts/vanilla/game/` and the official wiki for scope and type.
